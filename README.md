# CPS PJO Audit

Web Application สำหรับตรวจ PJO (Planned Job Observation) ตามแบบฟอร์ม **CATH-CPS009-B02 PJO Evaluation** ของ 7 Workshop
(GA, GA Inspection, BS, PS, LOG, PT Sub Line Engine, PT Battery) ใช้ได้บนมือถือ แท็บเล็ต และโน้ตบุ๊ก

> โครงการนี้แยกเป็นแอป Django (`pjo`, `org`) เพื่อย้ายเข้าเป็นโมดูล **Standardized Work → PJO** ของระบบ CPS ได้ในภายหลัง
> ถ้าย้ายเข้า CPS System ให้แทนที่ `org.models` (Workshop / Team / Employee / RoleAssignment) ด้วยตารางเดิมของ CPS
> แล้วคง `org/permissions.py` เป็นจุดเดียวที่ตรวจสิทธิ์

## เส้นทางหลัก

เลือก Workshop → เปิดฟอร์ม 4 ตาราง → ตรวจ (√ / × / N/A) → จับเวลา → บันทึกปัญหา → ส่งลงนาม → เซ็นบนมือถือ → ติดตามแก้ไข → ตรวจยืนยัน → Export PDF/Excel

| เมนู | สิ่งที่ทำ |
|---|---|
| Dashboard | แผนตรวจเดือนนี้, รอลงนาม, ความผิดปกติหลัก/รอง, ปัญหาเปิด/เกินกำหนด/รอตรวจยืนยัน/ซ้ำ, รอฝึกอบรม/รับรองใหม่ (เป็นจำนวนนับ ไม่มีคะแนนรวม) |
| แผนและรายการตรวจ PJO | วางแผนตรวจ และรายการ Audit ทั้งหมดพร้อมสถานะ |
| เริ่มตรวจ PJO | เลือกแม่แบบที่ Published และกรอกข้อมูลส่วนหัว |
| ติดตามปัญหา | Issue Center จากทั้ง 4 ตาราง กรองตาม Workshop / Team / ผู้รับผิดชอบ / สถานะ / Due Date |
| รายการรอลงนาม | Audit ที่ลงนามไม่ครบ และรายการรอฝึกอบรม/รับรองใหม่ |
| จัดการแม่แบบและมาตรฐาน | ดูแม่แบบพร้อมแหล่งอ้างอิง cell, Draft → Published → Retired, รายการรอยืนยัน, ความหมาย G/B/R |
| รายงานและ Export | PDF ใกล้เคียงแบบฟอร์ม 4 ตาราง, Excel ผลตรวจ, ทะเบียนปัญหา |

## หลักการที่ระบบยึด

- **คำถามจริงของแต่ละ Workshop** ดึงจากไฟล์ Excel ทุก worksheet พร้อมแหล่งอ้างอิง (ดู `docs/SOURCE_MAPPING.md`) และมีเทสต์เทียบกับไฟล์ต้นฉบับทุกครั้ง
- **มาตรฐานหลัก = แบบฟอร์ม Excel CATH-CPS009-B02 ของแต่ละ Workshop (มาตรฐานฉางอานระยอง)** · PDF 002 Standardization เป็นเอกสารอ้างอิง ความแตกต่างระหว่าง PDF กับ Excel บันทึกไว้ในหน้าแม่แบบ (P13–P21)
- **ไม่เดา**: สิ่งที่เอกสารไม่ได้กำหนดแสดงเป็น "รอยืนยัน" ในหน้าแม่แบบจนกว่าผู้ดูแลจะยืนยัน
- **G/B/R (ยืนยันแล้ว)**: G = Complete (ปิดแล้ว), B = On progress (ยังไม่ปิด ยังไม่เลยกำหนด), R = Overdue (ยังไม่ปิด เลยกำหนด) คำนวณอัตโนมัติจากสถานะปัญหาและ Due Date
- **การแก้ไขแม่แบบที่ผู้ดูแลยืนยัน** อยู่ใน `pjo/seed/corrections.json` (เช่น หัวตาราง PT Battery) `setup_pjo` สร้างเป็นเวอร์ชันใหม่ Published โดยเวอร์ชันเดิมเป็น Retired และ Audit เดิมไม่เปลี่ยน
- **ช่องว่าง = ยังไม่ได้ตรวจ** ไม่ใช่ผ่าน; ช่อง 1–12 คือ "ครั้งที่สังเกต" ไม่ตีความเป็นเดือน
- **Snapshot มาตรฐาน**: Audit เก็บสำเนามาตรฐานที่ใช้ แม่แบบเวอร์ชันใหม่ไม่เปลี่ยน Audit เก่า และเปลี่ยน Workshop หลังมีผลตรวจไม่ได้
- **Completed ≠ ปิดปัญหาครบ**: แสดง "ตรวจครบ แต่ยังมีปัญหาเปิด" และ "รอรับรองใหม่" แยกกัน
- **ระบบหลักทำงานได้โดยไม่มี AI** (AI เป็นส่วนเสริมภายหลัง)

## ฟังก์ชันสำคัญ

**ตาราง 1** ตารางเต็ม (ตรึงหัวตาราง/คอลัมน์คำถาม) บนจอใหญ่ และโหมด "ตรวจทีละครั้ง" บนมือถือ (แถบเลือกครั้ง 1–12 + ปุ่ม √ × N/A ขนาดนิ้ว) กด × แล้วเปิดหน้าต่างบันทึกปัญหาที่อ้างอิงข้อและครั้งอัตโนมัติ ถ่ายรูป/แนบไฟล์ได้ และเชื่อมกับปัญหาเดิมโดยเก็บประวัติการพบทุกครั้ง ความผิดปกติหลักมีขั้นตอนตอบสนองตามมาตรฐาน (แจ้งหัวหน้า → จัดการทันที → ฝึกอบรม → รับรองใหม่) และลายเซ็นรับทราบครั้งแรกแยกจากลายเซ็นหลังรับรองใหม่ โปรแกรมไม่ควบคุมเครื่องจักรและไม่อนุญาตกลับเข้าทำงานแทนผู้มีอำนาจ

**จับเวลา (ข้อวัดเวลา)** Start / Lap / Pause (ต้องระบุเหตุผล) / Stop / บันทึก / เริ่มใหม่ (ยืนยันก่อน) แยก "ครั้งที่สังเกต" กับ "รอบจับเวลา" คำนวณจาก timestamp (ไม่พึ่ง setInterval) จึงกู้คืนได้หลัง Refresh หรือสลับแท็บ ตรวจจับการขาดช่วงและการเปลี่ยนเวลาเครื่องให้ผู้ตรวจยืนยัน เก็บค่ารายรอบ เฉลี่ย ต่ำสุด สูงสุด จำนวนรอบที่ใช้ รอบที่ไม่ใช้ต้องมีเหตุผลและเก็บค่าเดิมไว้ กรอกเวลาภายนอกได้ (Manual + เหตุผล) Standard Time กับ Takt Time แยกกันพร้อมแหล่งที่มา ผลประเมินแสดง "รอประเมิน"

**ตาราง 2** หมวด A–D ตามต้นฉบับ √ = ไม่มีปัญหาและปรับปรุงไม่ได้, × = ผิดปกติและปรับปรุงได้ (ตามหมายเหตุฟอร์ม) ตารางบันทึกโอกาสปรับปรุงเชื่อมกับทะเบียนปัญหากลาง เพิ่มแถวได้ไม่จำกัด

**ตาราง 3** คำถามจริงคู่กับคำตอบที่คาดหวัง บันทึกคำตอบพนักงาน ผลก่อนสอน สิ่งที่ชี้แนะ ผลหลังสอน ผู้ประเมิน/เวลา ข้อเสนอแนะพนักงานแยกจากความผิดปกติ

**ตาราง 4** สถานการณ์ตัวอย่างและคำตอบที่พึงประสงค์ตามเอกสาร บันทึกคำตอบจริงและผลการชี้แนะ เพิ่มประสบการณ์จริงของพนักงานได้ แยก "สถานการณ์สมมติ" กับ "เกิดขึ้นจริง" สร้าง Issue ได้เฉพาะเหตุการณ์จริง (ไม่สร้างอัตโนมัติจากกรณีตัวอย่าง)

**ปัญหา** Open → Assigned → In Progress → Pending Verification → Closed และ Reopened (ต้องมีเหตุผล) Overdue คำนวณจาก Due Date ผู้รับผิดชอบส่งตรวจ ผู้มีสิทธิ์ Verifier เป็นผู้ปิด การแก้ × เป็น √ ไม่ลบประวัติปัญหา กดซ้ำ/Sync ซ้ำไม่สร้างปัญหาซ้ำ

**ลายเซ็น** เซ็นด้วยนิ้ว ปากกา หรือเมาส์ แสดงชื่อ บทบาท รายการที่เกี่ยวข้อง และข้อความที่กำลังลงนาม ป้องกันลายเซ็นว่าง เก็บผู้ลงนาม บทบาท วันเวลา วิธีระบุตัวตน Audit Revision และ SHA-256 ของข้อมูลที่เซ็น พนักงานที่ไม่มีบัญชียืนยันด้วยรหัสพนักงานโดยมีผู้ตรวจเป็นพยาน หลังเซ็นส่วนนั้นถูกล็อก แก้ไขต้อง "ขอแก้ไขหลังลงนาม" + เหตุผล ระบบสร้าง Revision ใหม่ เก็บข้อมูลและลายเซ็นเดิม และขอเซ็นใหม่เฉพาะส่วนที่ได้รับผลกระทบ

**ความน่าเชื่อถือ** Autosave ทุกการเปลี่ยนแปลงเป็นคำสั่งที่มี op id (ทำซ้ำได้ไม่เกิดผลซ้ำ) แสดงสถานะจริง: "บันทึกขึ้น server แล้ว", "กำลังบันทึก", "ยังไม่ถึง server · เก็บในเครื่องนี้ N รายการ (รอ Sync)" ตรวจจับการแก้พร้อมกัน (ช่องเดียวกัน / ส่วนหัว) แล้วแจ้งผู้ใช้แทนการเขียนทับ มี Audit Trail ไฟล์แนบและลายเซ็นเก็บนอกโฟลเดอร์สาธารณะและเปิดผ่านการตรวจสิทธิ์เท่านั้น เวลาเก็บเป็น UTC แสดงเป็น Asia/Bangkok

## บทบาทและสิทธิ์

กำหนดใน Django Admin (`/django-admin/` → Role assignments) ต่อ Workshop หรือทุก Workshop (เว้นว่าง)

| บทบาท | สิทธิ์ |
|---|---|
| Admin | ทุกอย่าง รวมถึงจัดการแม่แบบ ยืนยันประเด็นรอยืนยัน ตั้งค่า G/B/R |
| Auditor | สร้าง/แก้ไข Audit ใน Workshop ที่ได้รับ, จัดการปัญหา |
| TL/GL | เหมือน Auditor และลงนามผู้บังคับบัญชา |
| Employee | ผูกบัญชีกับรายชื่อพนักงาน ลงนามเฉพาะ Audit ของตัวเอง |
| Issue Owner | บันทึกการแก้ไขปัญหาที่ได้รับมอบหมายและส่งตรวจยืนยัน |
| Verifier | ตรวจยืนยันและปิดปัญหา |
| Viewer | ดูอย่างเดียว |

ทุกสิทธิ์บังคับที่ Backend รวมถึงไฟล์แนบ ลายเซ็น รายงาน และ Export

## ติดตั้งด้วย Docker

```bash
cp .env.example .env        # แก้ DJANGO_SECRET_KEY, POSTGRES_PASSWORD, DJANGO_ALLOWED_HOSTS
docker compose up -d --build
docker compose exec web python manage.py createsuperuser
```
เปิด `http://<server>:8000` คอนเทนเนอร์จะรัน migrations และโหลดแม่แบบ 7 Workshop (`setup_pjo`) ให้อัตโนมัติ
จากนั้นเข้า `/django-admin/` เพื่อเพิ่ม Team, รายชื่อพนักงาน (Employee) และกำหนดบทบาทผู้ใช้

## รันแบบ Development

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m playwright install chromium   # สำหรับ PDF บนเซิร์ฟเวอร์ (ไม่บังคับ)
cp .env.example .env && export $(grep -v '^#' .env | xargs)
python manage.py migrate
python manage.py setup_pjo
python manage.py createsuperuser
DJANGO_DEBUG=1 python manage.py runserver
```
ถ้าเซิร์ฟเวอร์ไม่มี Chromium ปุ่ม PDF จะแจ้งให้ใช้หน้า "พิมพ์" แล้วเลือก Save as PDF (A4 แนวนอน)

## แม่แบบมาตรฐาน

- ไฟล์ต้นฉบับอยู่ใน `source_docs/` ตัวดึงข้อมูลคือ `tools/extract_templates.py` ผลลัพธ์ JSON อยู่ที่ `pjo/seed/templates/`
- ถ้าได้ไฟล์ Excel ฉบับใหม่: วางใน `source_docs/` → `python tools/extract_templates.py source_docs pjo/seed/templates` → `python manage.py setup_pjo` ระบบจะสร้าง **Draft** เวอร์ชันใหม่ (ไม่แก้ Published เดิม) ให้ Admin ตรวจแล้ว Publish
- `python tools/build_source_mapping.py` สร้าง `docs/SOURCE_MAPPING.md` ใหม่
- ประเด็นรอยืนยันอยู่ใน `pjo/seed/pending_items.json` และหน้า "จัดการแม่แบบและมาตรฐาน"

## ทดสอบ

```bash
python manage.py test pjo
```
ครอบคลุม: คำถาม 7 Workshop ตรงไฟล์, ไม่มีผลตรวจตัวอย่างติดมา, การจับเวลา (Pause/รอบที่ไม่ใช้/Manual/แทนที่ค่าเดิม), × เชื่อมปัญหาถูกข้อและไม่สร้างซ้ำ, ความผิดปกติหลักและการรับรองใหม่, ลงนาม/ล็อก/แก้หลังลงนาม, สิทธิ์ข้าม Workshop และไฟล์ส่วนตัว, แม่แบบใหม่ไม่เปลี่ยนผลเก่า, Export ภาษาไทย
